# 05. 공연과 좌석

> 이 프로젝트에서 가장 헷갈리는 설계: **`venue`(물리 공연장)와 `event`(판매 공연)의 분리**.
> 왜 좌석이 `Seat`과 `EventSeat` 두 개로 나뉘는지, 공연 등록/검수 흐름은 어떤지 설명한다.

---

## 1. 핵심 한 장: 물리 ≠ 판매

```
venue 도메인 (물리적 실체 — 건물처럼 고정)
┌─────────────────────────────────────────┐
│ Venue   "잠실 종합운동장"                  │
│   └ Seat  A열 1번 (VIP), A열 2번 (VIP)…   │ ← 좌석 물리 배치. 공연과 무관.
└─────────────────────────────────────────┘
                  │  회차를 열 때마다
                  ▼
event 도메인 (판매 단위 — 갈아끼움)
┌─────────────────────────────────────────┐
│ Event         "아이유 콘서트 H.E.R."       │
│   └ EventSchedule  7/1 19:30 1회차        │ ← 언제, 어느 공연장에서
│        └ EventSeat  A열 1번 = 9.9만원,     │ ← 그 회차의 판매 좌석(가격·상태)
│           status=AVAILABLE                │
└─────────────────────────────────────────┘
```

> **물리 좌석(`Seat`) 하나가, 회차마다 판매 좌석(`EventSeat`)으로 새로 찍힌다.**
> 같은 A열 1번이라도 7/1 1회차와 7/2 2회차는 **다른 `EventSeat`**다. 그래서 회차별로 가격을 다르게, 매진 여부를 따로 관리할 수 있다.

이 분리 덕분에 "공연장은 그대로 두고 공연만 갈아끼우기"가 된다.

---

## 2. venue 도메인 — 공연장과 좌석 배치

### Venue: 좌석을 격자로 찍어낸다
[Venue.java](../src/main/java/com/ticketing/venue/domain/Venue.java)
```java
public List<Seat> assignSeats(int rowCount, int columnCount, List<SeatGradeRange> ranges) {
    List<Seat> result = new ArrayList<>();
    for (int row = 1; row <= rowCount; row++) {
        SeatGrade grade = resolveGrade(row, ranges);     // 이 행은 무슨 등급인가
        for (int col = 1; col <= columnCount; col++) {
            result.add(Seat.of(this, row, col, grade));   // (row, col) 좌석 생성
        }
    }
    return result;
}
```
- 공연장을 `rowCount × columnCount` 격자로 만들고, **행 구간별로 등급**(VIP/R/S/A)을 배정한다.
- `SeatGradeRange(grade, fromRow, toRow)`로 "1~2행 VIP, 3~4행 R…" 식 매핑.
- [Seat.java](../src/main/java/com/ticketing/venue/domain/Seat.java)에 `@UniqueConstraint(venue_id, seat_row, seat_column)` → 같은 공연장에 같은 좌표 좌석 중복 불가.

### Venue는 SOFT DELETE
```java
@SQLRestriction("deleted_at IS NULL")   // 조회 시 자동으로 삭제 안 된 것만
public class Venue extends BaseEntity {
    private LocalDateTime deletedAt;
    public void delete() { this.deletedAt = LocalDateTime.now(); }
}
```
종료된 공연장도 과거 주문·통계가 참조하므로 행을 안 지운다(CLAUDE.md §6.2). `Event`·`Review`도 동일 패턴.

`VenueController`(`/venues`)는 등록·수정·삭제는 ADMIN, 조회(GET)는 공개.

## 3. event 도메인 — 3층 구조

```
Event (공연)  1 ──── N  EventSchedule (회차)  1 ──── N  EventSeat (판매 좌석)
```

### Event — 공연 메타 + 상태 머신
[Event.java](../src/main/java/com/ticketing/event/domain/Event.java)
```java
public static Event create(...) {
    validatePeriod(startDate, endDate);            // 불변식: 종료일 < 시작일이면 거부
    return Event.builder()...status(EventStatus.PENDING).build();  // 등록 직후 검수 대기
}
public void approve() {
    if (status != PENDING) throw new BaseException(INVALID_EVENT_STATUS);
    this.status = APPROVED;
}
public boolean isOwnedBy(Long sellerId) { return seller.getId().equals(sellerId); }
```
`EventStatus`: `PENDING(검수 대기) → APPROVED(게시 중) / REJECTED(반려) → CLOSED(종료)`.

### EventSchedule — "언제, 어느 공연장, 몇 회차"
[EventSchedule.java](../src/main/java/com/ticketing/event/domain/EventSchedule.java)
```java
@UniqueConstraint(name = "uk_event_schedule", columnNames = {"event_id", "venue_id", "round_number"})
```
같은 공연·공연장에서 회차 번호 중복 방지. `roundNumber`는 등록 시 자동 채번:
```java
int nextRound = eventScheduleRepository.countByEventIdAndVenueId(eventId, venueId) + 1;
```

### EventSeat — 회차별 판매 좌석 (가격 + 상태)
[EventSeat.java](../src/main/java/com/ticketing/event/domain/EventSeat.java)
```java
private Integer price;                  // 회차마다 다를 수 있음
private EventSeatStatus status;         // AVAILABLE / RESERVED / HELD
@ManyToOne private Seat seat;           // 어느 물리 좌석인지

public void reserve() {
    if (status != AVAILABLE) throw new BaseException(SEAT_NOT_AVAILABLE);  // 불변식
    this.status = RESERVED;
}
public void cancel() { this.status = AVAILABLE; }
```
- `RESERVED`: 결제 완료로 확정 점유(DB).
- `HELD`: 임시 점유 — 단, **이건 DB가 아니라 Redis로 관리**한다([07 좌석선점](07_좌석선점_Redis.md) 참고). DB의 `status`는 `AVAILABLE`이어도 응답 시 Redis 점유를 조회해 `HELD`로 덧씌운다.

## 4. 회차 등록 — 물리 좌석을 판매 좌석으로 복제

[EventScheduleService.create()](../src/main/java/com/ticketing/event/service/EventScheduleService.java)
```java
@Transactional
public void create(Long eventId, EventScheduleCreateDto dto, Long sellerId) {
    Event event = ...;
    if (!event.isOwnedBy(sellerId)) throw new BaseException(EVENT_NOT_OWNED);  // 본인 공연만
    Venue venue = ...;

    int nextRound = eventScheduleRepository.countByEventIdAndVenueId(eventId, venueId) + 1;
    EventSchedule schedule = EventSchedule.create(venue, dto.getShowDateTime(), nextRound);
    event.addSchedule(schedule);

    List<Seat> seats = seatRepository.findByVenueId(venueId);        // 물리 좌석 전부
    Map<SeatGrade, Integer> priceMap = ... ;                         // 등급별 가격
    validateAllGradesPriced(seats, priceMap);                       // 빠진 등급 있으면 GRADE_PRICE_REQUIRED

    List<EventSeat> eventSeats = seats.stream()
        .map(seat -> EventSeat.create(schedule, seat, priceMap.get(seat.getSeatGrade())))  // 좌석→판매좌석
        .toList();
    eventSeatRepository.saveAll(eventSeats);
}
```
여기가 §1의 "물리 좌석이 회차마다 판매 좌석으로 찍힌다"가 실제로 일어나는 곳이다. 등급별 가격을 받아, 그 공연장의 모든 좌석을 그 회차 전용 `EventSeat`으로 복제한다. 등급 중 하나라도 가격이 안 들어오면 거부.

## 5. 공연 등록·검수 흐름 (셀러 ↔ 어드민)

```
[셀러] POST /events           → Event(PENDING) 생성
[셀러] POST /events/{id}/schedules → 회차 + 판매좌석 생성
[어드민] GET /admin/events/pending  → 검수 대기 목록
[어드민] POST /admin/events/{id}/approve → APPROVED (+ 이력)
        또는 /reject (반려 사유 필수)    → REJECTED (+ 이력)
[손님] GET /events            → APPROVED 이고 회차가 있는 것만 노출
```

### 검수는 이력을 남긴다
[AdminEventService.approve()](../src/main/java/com/ticketing/admin/service/AdminEventService.java)
```java
EventStatus prev = event.getStatus();
event.approve();
historyRepository.save(EventReviewHistory.of(event, ReviewAction.APPROVED, prev, event.getStatus(), null, adminMember));
```
[EventReviewHistory](../src/main/java/com/ticketing/event/domain/EventReviewHistory.java)에 누가(`reviewer`)·언제·무슨 액션·이전→이후 상태·사유를 남긴다. 반려는 사유가 필수(`REJECT_REASON_REQUIRED`).

## 6. 손님에게 보이는 공연 — 검색

[EventService.search()](../src/main/java/com/ticketing/event/service/EventService.java) → [EventRepositoryImpl](../src/main/java/com/ticketing/event/repository/EventRepositoryImpl.java)
```java
queryFactory.selectFrom(event)
    .where(event.status.eq(APPROVED),       // 게시 중인 것만
           event.schedules.isNotEmpty(),    // 회차가 하나라도 있어야 노출
           categoryEq(category),            // 필터 있으면 카테고리
           titleContains(keyword))          // 검색어 있으면 제목 LIKE
    .orderBy(event.id.desc()).fetch();
```
- `GET /events?category=CONCERT&q=아이유` 식. 카테고리/검색어는 동적(없으면 조건 제외).
- 상세 조회 `GET /events/{id}`는 `APPROVED`가 아니면 `PERFORMANCE_NOT_FOUND`로 막는다(검수 중 공연이 URL로 새지 않게).

> 현재 검색은 결과를 메모리에서 `EventListResponseDto`로 매핑하며 회차/좌석을 LAZY로 건드리면 N+1 소지가 있다. 코드에도 `// TODO ... N+1` 메모가 있고, 개선 전후 비교는 [13 성능](13_성능_before_after.md)에서 다룬다.

## 7. 캐시 — 지금은 꺼져 있다 (의도된 상태)

[CacheConfig.java](../src/main/java/com/ticketing/config/CacheConfig.java)는 `@Configuration`/`@EnableCaching`이 주석 처리돼 **비활성**이고, `EventService`·`AdminEventService`의 `@Cacheable`/`@CacheEvict`도 전부 주석이다.

- 의도: 공연 목록/상세는 읽기가 압도적이라 Redis 캐싱 1순위 후보지만, **성능 측정(before/after)을 위해 일부러 꺼둔 상태**다. 캐시를 켜기 전 N+1·인덱스 효과를 먼저 보려는 것.
- 켤 때 설계는 이미 잡혀 있다: 직렬화(`Jackson2JsonRedisSerializer` + `JavaTimeModule`), TTL 5분, null 캐싱 금지. 공연 수정/검수 시 `events`/`event` 캐시를 evict하는 자리도 주석으로 표시돼 있다.

> 프론트는 캐시 on/off와 무관하게 동일 응답을 받는다 — 캐시는 순수 백엔드 최적화다.

---

## 8. 면접 한 줄 정리

> 공연장의 물리 좌석(`Seat`)과 회차별 판매 좌석(`EventSeat`)을 분리해, 같은 좌석을 회차마다 다른 가격·상태로 팔 수 있게 했습니다. 공연은 셀러 등록 → 어드민 검수(이력 적재) → 게시의 상태 머신을 거치고, 임시 점유(HELD)는 DB가 아니라 Redis로 분리해 동시성 핫스팟을 DB 밖으로 뺐습니다.
