# 09. 선착순 쿠폰

> **선착순 100장 쿠폰을 어떻게 101장 발급 안 되게 막는가.**
> 재고 동시성 문제다. Redis 카운터를 원자적으로 깎고, 중복 발급은 Set으로 막는다. 그리고 Redis와 DB가 어긋날 때의 보상 처리까지.

---

## 1. 문제: 동시에 100명 넘게 누른다

쿠폰 100장에 5000명이 동시에 "발급" 버튼을 누른다. 막아야 할 두 가지:
1. **초과 발급**: 100장인데 101장 나가면 안 된다.
2. **중복 발급**: 한 사람이 여러 번 눌러 2장 받으면 안 된다.

순진하게 `SELECT count → if < 100 → INSERT`는 [07 §1](07_좌석선점_Redis.md)과 같은 Race Condition으로 깨진다.

---

## 2. 재고는 Redis 카운터로 — 원자적 감소

쿠폰을 만들 때 재고를 Redis에 심는다.
[CouponService.createCoupon()](../src/main/java/com/ticketing/coupon/service/CouponService.java)
```java
@Transactional
public Long createCoupon(CouponCreateDto dto) {
    Coupon coupon = couponRepository.save(Coupon.create(...));   // DB엔 쿠폰 메타(이름·할인·총수량)
    redisTemplate.opsForValue().set(stockKey(coupon.getId()),    // Redis엔 재고 카운터
        String.valueOf(dto.getTotalQuantity()));
    return coupon.getId();
}
// stockKey  = "coupon:stock:{id}"
// issuedKey = "coupon:issued:{id}"
```
재고 숫자는 **DB가 아니라 Redis**가 들고 있다. 발급 핫스팟을 DB 밖으로 빼기 위해서다.

---

## 3. 발급 — Set으로 중복 차단 + 카운터로 재고 차단

[CouponService.issue()](../src/main/java/com/ticketing/coupon/service/CouponService.java)
```java
@Transactional
public void issue(Long couponId, Long memberId) {
    Coupon coupon = ...; Member member = ...;
    String me = memberId.toString();

    // ① 중복 발급 차단: Set에 추가. 이미 있으면 added=0
    Long added = redisTemplate.opsForSet().add(issuedKey, me);
    if (added == null || added == 0) throw new BaseException(COUPON_ALREADY_ISSUED);

    // ② 재고 차단: 카운터를 원자적으로 1 깎음
    Long remaining = redisTemplate.opsForValue().decrement(stockKey);
    if (remaining == null || remaining < 0) {
        redisTemplate.opsForValue().increment(stockKey);     // 되돌리고
        redisTemplate.opsForSet().remove(issuedKey, me);     // 발급 기록도 취소
        throw new BaseException(COUPON_SOLD_OUT);             // 소진
    }

    // ③ 통과 → DB에 발급 내역 저장
    try {
        couponIssueRepository.save(CouponIssue.create(coupon, member));
    } catch (RuntimeException e) {
        // ④ DB 저장 실패 → Redis 보상(롤백)
        redisTemplate.opsForValue().increment(stockKey);
        redisTemplate.opsForSet().remove(issuedKey, me);
        throw e;
    }
}
```

### ① 중복 차단 — `SADD`의 반환값
Redis `SADD`는 **새로 추가됐으면 1, 이미 있으면 0**을 반환한다(원자적). `issued` Set에 memberId를 넣어 0이 나오면 이미 받은 사람 → `COUPON_ALREADY_ISSUED`. "한 명당 한 장"을 한 줄로 보장.

### ② 재고 차단 — `DECR`의 음수 판정
Redis `DECR`도 원자적이다. 동시에 5000명이 깎아도 순서대로 처리돼 정확히 100명까지만 `remaining >= 0`. 101번째부터 `remaining < 0` → 깎은 걸 `INCR`로 되돌리고 `COUPON_SOLD_OUT`. → **101장이 나갈 수 없다.**

순서가 중요하다: **중복 검사(①) → 재고 차감(②)**. 중복이면 재고를 안 건드리고 끝낸다.

## 4. Redis와 DB가 어긋나면? — 보상 트랜잭션

Redis 차감은 성공했는데(②) DB 저장(`CouponIssue`)이 실패하면(③), Redis 재고는 줄었는데 발급 내역은 없는 **불일치**가 생긴다. 그래서 ④에서 **Redis를 되돌린다**:
```java
catch (RuntimeException e) {
    redisTemplate.opsForValue().increment(stockKey);   // 재고 복구
    redisTemplate.opsForSet().remove(issuedKey, me);   // 발급권 복구
    throw e;
}
```
이게 **보상 트랜잭션(compensating transaction)**이다. Redis는 RDB 트랜잭션에 못 묶이므로, DB 실패 시 수동으로 되돌려 정합성을 맞춘다.

> 면접 포인트: "Redis와 DB는 한 트랜잭션이 아니다"를 이해하고 있다는 신호. 한계도 안다 — ④ 사이에 프로세스가 죽으면 보상이 안 돌 수 있다. 더 엄밀히는 Lua 스크립트(원자 처리)나 Redis Stream + 비동기 소비로 발급을 풀 수 있다. 학습 단계라 "차감 후 보상"으로 단순하게 갔다.

## 5. 좌석 선점 vs 쿠폰 — 같은 무기, 다른 자료구조

| | 좌석 선점 [(07)](07_좌석선점_Redis.md) | 선착순 쿠폰 |
|---|---|---|
| 막는 것 | 한 좌석 = 한 명 | 한 사람 = 한 장 + 총량 제한 |
| 핵심 명령 | `SET NX`(없을 때만 점유) | `SADD`(중복) + `DECR`(재고) |
| 임시성 | TTL 7분 (점유는 임시) | 영구 (발급은 확정) |
| 자료구조 | String(키=좌석) | Set(발급자) + String(재고 카운터) |

둘 다 "Redis 단일 스레드의 원자성"이라는 같은 원리를 쓰되, 요구가 달라 자료구조가 다르다.

- 발급 [CouponController](../src/main/java/com/ticketing/coupon/controller/CouponController.java): `POST /coupons/{id}/issue`(회원), `GET /coupons`(전체), `GET /coupons/me`(내 쿠폰). 쿠폰 **생성**(`POST /coupons`)은 ADMIN 전용.
- 시드 [DataSeedRunner.seedCoupon()](../src/main/java/com/ticketing/config/DataSeedRunner.java)에서 쿠폰 3종을 만들며 동시에 `coupon:stock:{id}`를 Redis에 세팅한다(DB 메타 + Redis 재고를 함께).
- `Coupon`은 할인 타입(`FIXED`/`RATE`)·할인값·총수량 메타만, 발급 관계는 `CouponIssue`(쿠폰↔회원)로 분리.

## 7. 면접 한 줄 정리

> 선착순 쿠폰은 재고를 Redis 카운터로 들고 `DECR`의 원자성으로 초과 발급을, `SADD` 반환값으로 1인 1매 중복을 막았습니다. 중복 검사 → 재고 차감 순서를 지키고, 차감 후 DB 저장이 실패하면 Redis를 되돌리는 **보상 트랜잭션**으로 정합성을 맞췄습니다. 발급 핫스팟을 DB가 아닌 Redis로 흡수하는 게 핵심입니다.
