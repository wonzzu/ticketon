# 01. 패키지 구조와 계층

> 이 문서는 **"왜 폴더를 이렇게 나눴고, 의존이 어느 방향으로 흐르는가"** 를 설명한다.
> 코드가 어디 있는지 찾는 지도이자, 면접에서 "계층 아키텍처를 왜 이렇게 짰나"에 답하기 위한 근거다.

---

## 1. 한 문장 요약

> 계층 아키텍처는 의존을 **없애는** 게 아니라 **한 방향으로 흐르게 강제**하는 것이고, 그 끝점이 도메인이다.

도메인(엔티티)이 바깥(Controller·DTO·인프라)을 **모를 때** 단독 테스트·재사용·이식이 가능해진다. 이 프로젝트는 그 원칙을 **폴더 구조로 강제**한다.

---

## 2. 전체 패키지 지도

```
com.ticketing
├── auth         인증/인가      로그인, JWT 발급·검증, 리프레시 토큰
├── member       회원           일반회원 / 셀러 / 어드민 (JOINED 상속)
├── venue        공연장(물리)   Venue + Seat (좌석 물리 배치)
├── event        공연(판매)     Event + EventSchedule + EventSeat + 좌석선점
├── reservation  예매           예매 생성, 멱등성, 좌석 연결
├── payment      결제           모의 결제, 예매와 1:1
├── coupon       쿠폰           선착순 발급
├── queue        대기열         줄 세우기 + 순번
├── review       리뷰           공연 후기, 평점
├── statistics   통계           일별 매출/공연 집계 + 랭킹
├── admin        어드민         공연 검수, 회원 관리
├── global       공통           BaseResponse, BaseEntity, 예외, RateLimit
└── config       설정           Security, Redisson, JPA Auditing, QueryDSL
```

## 3. 도메인 내부는 항상 같은 5단 구조

`member`를 예로 들면:

```
member/
├── domain/        Entity·VO·ENUM           (Member, MemberStatus, MemberType…)
│   └── ※ DB와 매핑되는 핵심 모델. 가장 안쪽 계층.
├── dto/
│   ├── request/   들어오는 데이터 (검증)    (NormalMemberSignupDto…)
│   └── response/  나가는 데이터 (변환)       (MyInfoResponseDto…)
├── repository/    DB 접근                   (MemberRepository, MemberRepositoryImpl)
├── service/       비즈니스 로직 (트랜잭션)   (NormalMemberService…)
└── controller/    HTTP 진입점               (NormalMemberController…)
```

### 왜 `domain/`과 `dto/`를 폴더로 갈랐나 (★ 핵심 설계)

엔티티가 DTO를 import하면 **의존 방향이 역전**된다(도메인이 바깥을 알게 됨 → DDD 위반). 폴더가 갈려 있으면 그 위반이 **import 한 줄로 눈에 보인다.**

- 엔티티가 `com.ticketing.member.dto.~`를 import → **🚨 위반 신호**
- DTO가 `com.ticketing.member.domain.~`를 import → **✅ 정상** (DTO는 엔티티를 알아도 됨)

`model/` 한 덩어리에 엔티티·DTO를 섞어 넣었다면 이 위반이 시각적으로 안 잡힌다. 폴더 분리만으로 규칙을 강제한 것이다.

---

## 4. 의존 방향 — 정상 vs 위반

```
Controller ──→ Service ──→ Repository
     │            │             │
     └────────────┴─────────────┘
                  ↓
               Domain  ← 가장 안쪽. 외부를 모름.
```

| 의존 | 정상? | 이 프로젝트에서 |
|---|---|---|
| Controller → Service / DTO | ✅ | `EventController` → `EventService` |
| Service → Repository / Domain | ✅ | `EventService` → `EventRepository`, `Event` |
| **DTO → Entity** | ✅ | `EventResponseDto.from(Event)` |
| **Entity → DTO** | ❌ | 이 프로젝트엔 없음 (의도적) |
| Entity → Service | ❌ | 없음 |

실제 코드로 확인해 보면:
- `EventResponseDto.from(Event event)` → DTO가 엔티티를 안다 (정상).
- `Event.create(title, description, …, Seller seller)` → 엔티티 정적 팩토리가 **원시값·VO만** 받는다. DTO를 받지 않는다 (정상). → [10.6 정적 팩토리 가이드](../CLAUDE.md) 그대로.

## 5. 각 계층이 실제로 하는 일 (코드 근거)

### 5.1 Controller — 얇다
[NormalMemberController.java](../src/main/java/com/ticketing/member/controller/NormalMemberController.java)
```java
@PostMapping("/signup")
public ResponseEntity<BaseResponse<Void>> signup(@Validated @RequestBody NormalMemberSignupDto dto) {
    normalMemberService.create(dto);                       // 서비스에 위임만
    return ResponseEntity.status(HttpStatus.CREATED).body(BaseResponse.success());
}
```
- 입력 받기(`@RequestBody`), 형식 검증(`@Validated`), 응답 래핑(`BaseResponse`)만 한다.
- 로그인 사용자는 `@AuthenticationPrincipal CustomUserDetails user`로 받아 `user.getMemberId()`만 서비스로 넘긴다.

### 5.2 Service — DTO를 풀어 도메인에 위임
[NormalMemberService.java](../src/main/java/com/ticketing/member/service/NormalMemberService.java)
```java
@Transactional
public void create(NormalMemberSignupDto dto) {
    if (memberRepository.existsByEmail(dto.getEmail())) throw new BaseException(DUPLICATE_EMAIL);
    if (normalMemberRepository.existsByNickname(dto.getNickname())) throw new BaseException(DUPLICATE_NICKNAME);

    NormalMember m = NormalMember.create(            // DTO를 풀어서 (dto.getX()...)
        dto.getEmail(),
        passwordEncoder.encode(dto.getPassword()),   // 외부 의존(인코더)은 Service가 처리
        dto.getName(), dto.getNickname(), ... );
    normalMemberRepository.save(m);
}
```
- **DTO 언패킹**(`dto.getX()`)은 Service의 책임이다. 엔티티는 원시값만 받는다.
- **외부 의존**(`passwordEncoder`)은 Service가 처리하고, 인코딩된 결과만 엔티티에 넘긴다.
- `@Transactional` 경계도 Service가 잡는다. 클래스는 `@Transactional(readOnly = true)`, 쓰기 메서드만 `@Transactional`을 덧붙이는 패턴이 전 도메인 공통이다.

### 5.3 Domain(Entity) — 도메인 규칙/불변식만
[Member.java](../src/main/java/com/ticketing/member/domain/Member.java)
```java
public void suspend() {
    if (this.memberStatus == MemberStatus.WITHDRAWN) {  // 불변식: 탈퇴 회원은 정지 불가
        throw new BaseException(INVALID_MEMBER_STATUS);
    }
    this.memberStatus = MemberStatus.SUSPENDED;
}
```
- 상태 변경은 **setter가 아니라 의미 있는 도메인 메서드**(`suspend()`, `release()`, `withdraw()`)로만 한다.
- 검증/불변식이 엔티티 안에 있다(`Event.validatePeriod()`, `Review.validateRating()`).

### 5.4 Repository — 인터페이스 + QueryDSL 구현
- 정적 쿼리: Spring Data JPA 메서드(`existsByEmail`, `findByStatus`).
- 동적 쿼리: `XxxRepositoryCustom` 인터페이스 + `XxxRepositoryImpl`(QueryDSL). → [10 리뷰·페이징](10_리뷰_페이징.md)에서 자세히.

> 학습 단계라 Repository 인터페이스를 `repository/`에 두고 헥사고날의 "포트를 domain에" 단계까지는 안 갔다. 의존 방향(Service는 인터페이스에만 의존)은 이미 지켜진다.

## 6. global — 도메인이 아닌 공통 인프라

`global`은 도메인 단위가 아니라 **횡단 관심사**라서 5단 구조를 따르지 않는다.

| 위치 | 역할 | 문서 |
|---|---|---|
| `global/baseresponse` | `BaseResponse`(응답 래퍼), `BaseResponseStatus`(에러 코드 ENUM) | [02](02_요청_한번의_생애.md) |
| `global/entity` | `BaseEntity`(생성/수정 추적), `Address`(공유 VO) | [12](12_이력_통계_배치.md) |
| `global/exception` | `BaseException`, `GlobalExceptionHandler` | [02](02_요청_한번의_생애.md) |
| `global/ratelimit` | `@RateLimit` + AOP | [11](11_Redis_총정리_RateLimit.md) |

## 7. 흔한 실수 체크리스트 (이 프로젝트는 다 통과)

- [x] 엔티티가 Request DTO를 import → **안 함**
- [x] 엔티티 정적 팩토리가 `from(dto)` → **안 함** (`create(원시값…)`만)
- [x] 엔티티가 Service 호출 → **안 함**
- [x] `Entity.update(dto)`로 검증 없이 통째 교체 → **안 함** (`update(원시값…)` + 내부 검증)
