# 12. 이력 · 통계 · 배치

> 예매·결제 변경을 **왜, 어떻게 이력으로 보존**하는지, 일별 매출/공연 **통계를 어떻게 집계**하는지,
> 그리고 그 집계를 **배치로 돌릴 때 멱등성**을 어떻게 지키는지 — 운영/면접에서 "왜?"에 답하기 위한 문서다.

---

## 1. 두 가지 다른 것: 이력 vs 통계

| | 이력(History) | 통계(Statistics) |
|---|---|---|
| 목적 | "이 건이 언제 어떻게 바뀌었나" 추적·분쟁 대응 | "어제 매출 얼마, 어느 공연이 잘 팔렸나" 집계 |
| 단위 | 행 단위 스냅샷 | 날짜·공연 단위 합계 |
| 적재 시점 | 상태가 바뀔 때마다 | 하루 한 번 배치 |
| 테이블 | `*_history` | `daily_*_stats` |

---

## 2. 이력 — 전체 행 스냅샷

CLAUDE.md §6.3대로 **핵심 도메인만** 이력을 남긴다. 이 프로젝트의 이력 테이블:

| 이력 테이블 | 대상 | 적재 시점 |
|---|---|---|
| `ReservationHistory` | 예매 | 생성·확정·취소 |
| `PaymentHistory` | 결제 | 결제·취소 |
| `EventReviewHistory` | 공연 검수 | 승인·반려 |
| `MemberHistory` | 회원 상태 | 정지·해제 |

### 스냅샷 방식 — 매 변경마다 한 행
[ReservationHistory.java](../src/main/java/com/ticketing/reservation/domain/ReservationHistory.java)
```java
public static ReservationHistory of(Reservation reservation) {       // 일반 상태 스냅샷
    return ReservationHistory.builder()
        .reservationId(reservation.getId())
        .status(reservation.getStatus())        // 그 순간의 상태
        .totalPrice(reservation.getTotalPrice())// 그 순간의 가격
        .build();
}
public static ReservationHistory ofCancel(Reservation r, CancelReason reason, String detail) {  // 취소 전용
    return ...cancelReason(reason).reason(detail)...;
}
```
예매 흐름에서 **상태가 바뀔 때마다** 이력을 쌓는다([06](06_예매_결제.md)):
- 생성 직후 `of(reservation)` → status=PENDING 스냅샷
- 결제 확정 후 `of(reservation)` → status=CONFIRMED 스냅샷
- 취소 시 `ofCancel(...)` → status=CANCEL + 사유

→ **INSERT 시점부터 이력을 남긴다**(CLAUDE.md §6.3 "이력 끊김 방지"). 한 예매의 생애가 끊기지 않고 추적된다.

### 왜 FK 없이 `reservationId`만 들고 있나
`ReservationHistory`·`PaymentHistory`는 원본 엔티티 참조(`@ManyToOne`)가 아니라 **ID 값(`Long reservationId`/`paymentId`)만** 들고 있다.
- 이력은 "그 순간의 사실"을 박제하는 것이라 원본과 연결고리(FK)를 강제할 필요가 없다.
- 원본이 나중에 바뀌어도 이력 스냅샷은 그대로 보존돼야 한다.
- 대용량 적재 테이블에 FK를 안 거는 성능 원칙(CLAUDE.md §6.8)과도 맞는다.

> 비교: `EventReviewHistory`·`MemberHistory`는 `@ManyToOne`으로 원본을 참조한다. 이쪽은 적재량이 적고 어드민 화면에서 원본과 함께 보여주므로 연관관계를 택한 차이.

### 이력은 면접 어필 1순위
"주문 당시 가격이 얼마였냐" 같은 분쟁에 답할 수 있다는 게 핵심. 가격·상태가 나중에 바뀌어도 **그 시점 스냅샷**이 남아 있다.

## 3. 통계 — 일별 테이블 두 개

[DailySalesStats](../src/main/java/com/ticketing/statistics/domain/DailySalesStats.java) · [DailyEventStats](../src/main/java/com/ticketing/statistics/domain/DailyEventStats.java)
```java
DailySalesStats  : statDate(UNIQUE), orderCount, salesAmount       // 하루 전체 매출
DailyEventStats  : (statDate, eventId)UNIQUE, orderCount           // 하루 공연별 주문수
```
CLAUDE.md §6.4: **일별 테이블 1개로 시작, 주간/월간은 GROUP BY.** 별도 집계 테이블을 안 만든다.

## 4. 집계 로직 — 멱등성이 핵심

[StatisticsService.aggregateDaily()](../src/main/java/com/ticketing/statistics/service/StatisticsService.java)
```java
@Transactional
public void aggregateDaily(LocalDate date) {
    LocalDateTime start = date.atStartOfDay();
    LocalDateTime end = date.plusDays(1).atStartOfDay();

    PaymentSalesAggregate agg = paymentRepository.aggregatePaid(start, end);   // 그날 PAID 합계

    dailySalesStatsRepository.deleteByStatDate(date);                          // ★ DELETE
    dailySalesStatsRepository.save(DailySalesStats.of(date, agg.orderCount(), agg.salesAmount())); // INSERT

    dailyEventStatsRepository.deleteByStatDate(date);                          // ★ DELETE
    paymentRepository.aggregatePaidByEvent(start, end)                         // 공연별 그룹 집계
        .forEach(e -> dailyEventStatsRepository.save(DailyEventStats.of(date, e.eventId(), e.orderCount())));
}
```

### DELETE & INSERT — 왜?
배치가 **두 번 돌아도** 결과가 같아야 한다(멱등성). 만약:
```java
// ❌ 절대 금지 (CLAUDE.md §6.4)
UPDATE daily_stats SET orderCount = orderCount + value
```
이렇게 누적하면 배치가 재실행될 때 **숫자가 뻥튀기**된다. 그래서 그 날짜 통계를 **지우고 새로 넣는다**(`deleteByStatDate` → `save`). 몇 번을 돌려도 그날의 정답으로 수렴한다.

집계 쿼리는 QueryDSL [PaymentRepositoryImpl](../src/main/java/com/ticketing/payment/repository/PaymentRepositoryImpl.java):
```java
// 전체 매출
.select(Projections.constructor(PaymentSalesAggregate.class,
        payment.count(), payment.amount.sum().coalesce(0).longValue()))
.where(payment.status.eq(PAID), createdBetween(start, end))

// 공연별 (reservation 조인 후 event.id로 GROUP BY)
.select(Projections.constructor(EventOrderCount.class, reservation.eventSchedule.event.id, payment.count()))
.groupBy(reservation.eventSchedule.event.id)
```
`Projections.constructor`로 엔티티가 아닌 **집계 전용 DTO**에 바로 담는다(불필요한 엔티티 로딩 회피).

## 5. 배치 — 새벽 4시 자동 실행

[DailySalesStatsScheduler](../src/main/java/com/ticketing/statistics/batch/DailySalesStatsScheduler.java)
```java
@Scheduled(cron = "0 0 4 * * *")          // 매일 04:00
public void aggregateYesterday() {
    LocalDate target = LocalDate.now().minusDays(1);   // 어제치 집계
    try { statisticService.aggregateDaily(target); }
    catch (Exception e) { log.error("[배치] 일별 통계 집계 실패: date={}", target, e); }
}
```
- 어제 데이터는 자정이 지나면 더 안 바뀌므로 새벽에 안전하게 집계.
- 실패해도 예외를 삼키고 로그만 남긴다(다음 날 배치나 수동 재실행으로 복구 — DELETE&INSERT라 재실행 안전).
- 수동 트리거도 있다: `POST /admin/stats/aggregate?date=` ([AdminStatsController](../src/main/java/com/ticketing/statistics/controller/AdminStatsController.java)).

## 6. 조회 — 과거는 통계, 오늘은 실시간 (하이브리드)

오늘치는 아직 배치를 안 돌렸다. 그래서 **과거는 통계 테이블, 오늘은 실시간 집계**를 합쳐 준다(CLAUDE.md §6.4 하이브리드).
[StatisticsService.findRange()](../src/main/java/com/ticketing/statistics/service/StatisticsService.java)
```java
LocalDate pastTo = to.isBefore(today) ? to : today.minusDays(1);
if (!from.isAfter(pastTo))
    dailySalesStatsRepository.findByStatDateBetween...(from, pastTo)  // 과거: 집계 테이블에서
        .forEach(s -> result.add(DailySalesStatsResponseDto.from(s)));

if (!to.isBefore(today) && !from.isAfter(today)) {
    PaymentSalesAggregate t = paymentRepository.aggregatePaid(today..., 내일...);  // 오늘: payment 실시간
    result.add(DailySalesStatsResponseDto.ofToday(today, t.orderCount(), t.salesAmount()));
}
```
`GET /admin/stats/daily?from=&to=` → 어드민 통계 화면. 과거는 가볍게(미리 집계됨), 오늘은 최신값으로.

## 7. 랭킹 — 통계 테이블의 또 다른 용도

"인기순(판매량) 공연"은 일별 공연 통계를 합산해 뽑는다.
[DailyEventStatsRepository](../src/main/java/com/ticketing/statistics/repository/DailyEventStatsRepository.java)
```java
@Query("select d.eventId from DailyEventStats d where d.statDate >= :from " +
       "group by d.eventId order by sum(d.orderCount) DESC")
List<Long> findRankedEventIds(LocalDate from, Pageable pageable);
```
[StatisticsService.getRanking()](../src/main/java/com/ticketing/statistics/service/StatisticsService.java)
```java
List<Long> ids = "rating".equals(sort)
    ? reviewRepository.findTopRatedEventIds(APPROVED, MIN_REVIEWS, limit)   // 평점순 → 리뷰 집계 [10]
    : dailyEventStatsRepository.findRankedEventIds(today.minusDays(days), ...); // 인기순 → 통계 집계
return toRanked(ids);   // id 순서 유지하며 Event 매핑
```
`GET /events/ranking?sort=popular&days=7` → 최근 7일 판매량 TOP. `sort=rating`이면 [10 §5](10_리뷰_페이징.md)의 평점 랭킹으로 분기. ID 목록을 먼저 뽑고 `findAllById`로 엔티티를 한 번에 조회해 N+1을 피한다.

## 8. 로그 vs 비즈니스 데이터

CLAUDE.md §6.9대로, DB엔 **비즈니스 이력/통계만** 둔다. 시스템 로그(접근·디버그)는 파일로:
```properties
logging.file.name=logs/ticketing.log    # 롤링 10MB, 7일, 100MB cap
```
중요 비즈니스 이벤트(로그인·예매·결제·승급·발급)는 `log.info`로 남기지만, 이건 **운영 가시성용 로그**지 DB 이력과 다르다.

## 9. 면접 한 줄 정리

> 핵심 도메인(예매·결제·검수·회원)은 상태가 바뀔 때마다 `*_history`에 스냅샷을 남겨 "그 시점의 사실"을 박제합니다. 통계는 일별 테이블 하나로 두고 주간/월간은 GROUP BY로 파생하며, 배치는 **DELETE & INSERT**로 멱등성을 보장해 재실행해도 숫자가 뻥튀기되지 않습니다. 오늘치는 통계 테이블 대신 실시간 집계를 합치는 하이브리드로 응답합니다.
