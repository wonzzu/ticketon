# 04. 회원 도메인

> 회원이 **일반회원 / 셀러 / 어드민** 세 종류로 나뉘는데, 이걸 어떻게 한 테이블 묶음으로 깔끔하게 매핑했는가.
> JPA 상속(JOINED) 전략과, 회원 상태 생명주기, 변경 이력(MemberHistory)을 다룬다.

---

## 1. 회원은 한 종류가 아니다

| 타입 | 고유 필드 | 가입 경로 |
|---|---|---|
| `NormalMember` (일반회원) | 닉네임, 생년월일, 성별 | `POST /members/signup` |
| `Seller` (판매자) | 회사명, 대표자명, 사업자번호 | `POST /sellers/signup` |
| `AdminMember` (관리자) | 부서, 사번 | 시드로만 생성(가입 API 없음) |

공통(이메일·비번·이름·전화·주소·상태)은 같지만 고유 필드가 다르다. 이걸 어떻게 매핑하느냐가 이 도메인의 핵심.

---

## 2. JPA 상속 — JOINED 전략

[Member.java](../src/main/java/com/ticketing/member/domain/Member.java)
```java
@Entity
@Inheritance(strategy = InheritanceType.JOINED)        // ★ 조인 전략
@DiscriminatorColumn(name = "member_type")             // 구분 컬럼
public abstract class Member extends BaseEntity {
    @Id @GeneratedValue(strategy = IDENTITY) private Long id;
    @Column(unique = true) private String email;
    private String password, name, phone;
    @Enumerated(STRING) private MemberType memberType;     // NORMAL/SELLER/ADMIN
    @Enumerated(STRING) private MemberStatus memberStatus; // 생명주기 상태
    @Embedded private Address address;
}
```
```java
@Entity @DiscriminatorValue("NORMAL")
public class NormalMember extends Member { private String nickname; ... }
```

### JOINED가 만드는 테이블 모양
```
member            (id, email, password, name, phone, member_type, member_status, address…)
  ├─ normal_member (id→member.id, nickname, birth_date, gender)
  ├─ seller        (id→member.id, company_name, representative_name, business_number)
  └─ admin_member  (id→member.id, department, employee_number)
```
- 공통은 `member`, 고유 필드는 각 자식 테이블. 자식 PK가 곧 부모 FK.
- `NormalMember` 조회 시 `member JOIN normal_member`로 합쳐 가져온다.

### 왜 JOINED인가 (면접 포인트)
- **SINGLE_TABLE**: 한 테이블에 다 몰아넣음 → 자식 고유 컬럼이 전부 **nullable**이 돼야 함. 셀러 필드가 일반회원 행에선 NULL. 제약(NOT NULL)을 못 건다.
- **JOINED**: 정규화됨. `nickname NOT NULL`, `business_number UNIQUE` 같은 제약을 **자식 테이블에 제대로** 걸 수 있다. 조인 비용은 있지만 데이터 정합성을 택했다.
- CLAUDE.md §6.5의 "분리할 땐 JOINED 우선" 원칙 그대로.

> 구현 메모: `member_type` 컬럼은 `@DiscriminatorColumn`이 관리하므로 엔티티 필드는 `insertable=false, updatable=false`로 읽기 전용 매핑돼 있다. 가입할 때 타입을 따로 안 넣어도 `@DiscriminatorValue`가 자동으로 박는다.

## 3. 정적 팩토리 — 초기 상태는 엔티티가 정한다

[NormalMember.create()](../src/main/java/com/ticketing/member/domain/NormalMember.java)
```java
public static NormalMember create(String email, String encodedPassword, String name,
                                  String nickname, LocalDate birthDate, Gender gender,
                                  String phone, Address address) {
    return NormalMember.builder()
        .email(email).password(encodedPassword)   // 이미 인코딩된 비번을 받음 (인코딩은 Service 책임)
        .name(name).nickname(nickname)...
        .memberStatus(MemberStatus.PENDING)        // ★ 초기 상태를 엔티티가 결정
        .build();
}
```
- 비번은 **인코딩된 상태로** 받는다. `passwordEncoder`는 외부 의존이라 Service가 처리하고 결과만 넘긴다(DDD 원칙).
- 가입 직후 상태 `PENDING`(이메일 인증 전)을 **엔티티가** 못 박는다. Service가 빌더로 직접 설정하지 않는다 → CLAUDE.md §10.7 체크리스트 통과.
- `AdminMember`만 `create()`에서 곧장 `ACTIVE`로 시작(관리자는 인증 절차 없음).

## 4. 회원 상태 생명주기

[MemberStatus.java](../src/main/java/com/ticketing/member/domain/MemberStatus.java)
```
PENDING(인증 전) → ACTIVE(정상) ⇄ SUSPENDED(정지)
                       ↓
                  WITHDRAWN(탈퇴)        DORMANT(휴면, 현재 미사용)
```

상태 전이는 전부 **도메인 메서드**로만, 불변식을 끼고 일어난다.
[Member.java](../src/main/java/com/ticketing/member/domain/Member.java)
```java
public void withdraw() { this.memberStatus = MemberStatus.WITHDRAWN; }

public void suspend() {
    if (memberStatus == WITHDRAWN) throw new BaseException(INVALID_MEMBER_STATUS); // 탈퇴자는 정지 불가
    this.memberStatus = SUSPENDED;
}
public void release() {
    if (memberStatus != SUSPENDED) throw new BaseException(INVALID_MEMBER_STATUS); // 정지 상태만 해제 가능
    this.memberStatus = ACTIVE;
}
```
이 상태는 [03 인증](03_인증인가.md)과 직결된다: `SUSPENDED`면 로그인 거부, `WITHDRAWN`/`DORMANT`면 `isEnabled()=false`.

## 5. 탈퇴는 SOFT인가? — 상태로 관리

CLAUDE.md §6.2 표에서 회원은 "SOFT DELETE(`deleted_at`)"로 적혀 있지만, **실제 구현은 `MemberStatus.WITHDRAWN` 상태값으로 관리**한다(`deleted_at` 컬럼 없음). 행을 지우지 않으니 주문 이력·복구가 보존되는 효과는 동일하다.

> 비교: `Venue`·`Event`·`Review`는 `@SQLRestriction("deleted_at IS NULL")` + `deletedAt` 컬럼으로 진짜 SOFT DELETE를 쓴다([05](05_공연_좌석.md)). 회원은 상태 머신이 이미 있어 상태값으로 충분하다고 본 차이다.

## 6. 일반회원 / 셀러 흐름 (CRUD)

[NormalMemberController](../src/main/java/com/ticketing/member/controller/NormalMemberController.java) · [SellerController](../src/main/java/com/ticketing/member/controller/SellerController.java)

| 동작 | 엔드포인트 | 검증 포인트 |
|---|---|---|
| 가입 | `POST /members/signup`, `/sellers/signup` | 이메일 중복(`DUPLICATE_EMAIL`), 닉네임 중복(`DUPLICATE_NICKNAME`, 일반회원만) |
| 내 정보 | `GET /members/me`, `/sellers/me` | 토큰의 memberId로 조회 |
| 수정 | `PATCH /members/me`, `/sellers/me` | 도메인 메서드 `changeMember()`/`update()`로 일부 필드만 |
| 탈퇴 | `DELETE /members/me`, `/sellers/me` | `member.withdraw()` |

수정은 setter가 아니라 의미 있는 메서드로:
```java
member.changeMember(dto.getNickName(), dto.getPhone(), dto.getAddress());  // 변경 가능 필드만
```
이메일·생년월일처럼 못 바꾸는 건 메서드 파라미터에 아예 없다 → "통째 교체" 안티패턴 회피.

> `MemberController`(`/me`)는 타입 무관 공통 내 정보(`MyInfoResponseDto`)를 주고, `NormalMemberController`(`/members/me`)는 일반회원 상세를 준다. 프론트 쓰임에 따라 분리.

## 7. 어드민 회원 관리 + 변경 이력

[AdminMemberService](../src/main/java/com/ticketing/admin/service/AdminMemberService.java) — `/admin/members` (ADMIN 전용)

### 검색은 QueryDSL 동적 쿼리 + 페이징
[MemberRepositoryImpl](../src/main/java/com/ticketing/member/repository/MemberRepositoryImpl.java)
```java
queryFactory.selectFrom(member)
    .where(emailContains(cond.email()), nameContains(cond.name()),
           statusEq(cond.memberStatus()), typeEq(cond.memberType()))  // null이면 조건 제외
    .orderBy(member.createdAt.desc())
    .offset(...).limit(...).fetch();
```
각 조건 메서드는 값이 없으면 `null`을 반환 → QueryDSL `where(null)`은 무시되므로, **입력된 필터만** AND로 붙는 동적 검색이 된다. (같은 패턴이 예매·공연 검색에도 반복됨 → [10](10_리뷰_페이징.md))

### 정지/해제 시 이력을 남긴다
[AdminMemberService.suspend()](../src/main/java/com/ticketing/admin/service/AdminMemberService.java)
```java
@Transactional
public void suspend(Long memberId, String reason) {
    Member member = ...;
    MemberStatus prev = member.getMemberStatus();   // 1) 이전 상태 캡처
    member.suspend();                                // 2) 도메인 메서드로 상태 변경(+불변식)
    memberHistoryRepository.save(                    // 3) 변경 이력 적재
        MemberHistory.of(member, prev, member.getMemberStatus(), reason));
}
```

[MemberHistory.java](../src/main/java/com/ticketing/member/domain/MemberHistory.java) — `previousStatus → newStatus`와 `reason`을 스냅샷으로 남긴다. "이 회원이 언제, 왜 정지됐나"를 추적할 수 있다. 어드민 상세 화면(`GET /admin/members/{id}`)에서 이 이력을 같이 내려준다.

> 이력 테이블 설계 철학은 [12 이력·통계·배치](12_이력_통계_배치.md)에 모았다. 회원 이력은 "선택 적용(△)" 대상이지만 정지/해제 사유 추적 용도로 넣었다.

---

## 8. 면접 한 줄 정리

> 회원 타입을 JPA **JOINED 상속**으로 매핑해 자식별 고유 컬럼에 NOT NULL·UNIQUE 제약을 정상적으로 걸었고, 상태 전이는 전부 도메인 메서드(`suspend`/`release`/`withdraw`)에 불변식과 함께 캡슐화했습니다. 관리자 상태 변경은 `MemberHistory`로 사유까지 스냅샷을 남깁니다.
