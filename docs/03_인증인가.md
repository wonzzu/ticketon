# 03. 인증 / 인가

> 로그인하면 무슨 일이 벌어지고, **그 다음 요청은 어떻게 "이 사람이 누구인지"를 아는가**.
> 세션을 안 쓰는 Stateless JWT 방식과, Access/Refresh 토큰을 나눠 쓰는 이유를 설명한다.

---

## 1. 두 단어부터: 인증 vs 인가

- **인증(Authentication)**: "너 누구냐" — 로그인. 이메일/비번 맞는지 확인하고 토큰을 준다.
- **인가(Authorization)**: "너 이거 할 자격 있냐" — 어드민만 `/admin/**`, 셀러만 공연 등록.

이 프로젝트는 **세션을 안 만든다**(`SessionCreationPolicy.STATELESS`). 서버가 "누가 로그인했는지" 기억하지 않고, 매 요청마다 토큰을 까서 판단한다. → 서버를 여러 대로 늘려도 세션 동기화가 필요 없다(확장 친화적).

---

## 2. 로그인 — 토큰 두 개를 받는다

[AuthService.login()](../src/main/java/com/ticketing/auth/service/AuthService.java)
```java
public TokenPair login(LoginRequestDto dto) {
    // 1) Spring Security의 AuthenticationManager가 이메일/비번 검증
    Authentication auth = authenticationManager.authenticate(
        new UsernamePasswordAuthenticationToken(dto.getEmail(), dto.getPassword()));

    CustomUserDetails principal = (CustomUserDetails) auth.getPrincipal();
    Long memberId = principal.getMemberId();
    String role = principal.getMember().getMemberType().name();   // NORMAL / SELLER / ADMIN

    // 2) 토큰 두 개 발급
    String accessToken  = jwtTokenProvider.createAccessToken(memberId, role);
    String refreshToken = jwtTokenProvider.createRefreshToken(memberId);

    // 3) Refresh는 Redis에 저장 (서버가 무효화할 수 있도록)
    refreshTokenStore.save(memberId, refreshToken);
    return new TokenPair(accessToken, refreshToken);
}
```

비번 검증은 직접 안 한다. `authenticationManager.authenticate(...)`가 내부적으로:
1. `CustomUserDetailsService.loadUserByUsername(email)`로 회원을 DB에서 찾고
2. `BCryptPasswordEncoder`로 비번을 대조하고
3. `CustomUserDetails.isEnabled()` / `isAccountNonLocked()`로 계정 상태(정지·탈퇴)를 검사한다.

[CustomUserDetails.java](../src/main/java/com/ticketing/auth/CustomUserDetails.java)
```java
@Override public boolean isAccountNonLocked() {
    return member.getMemberStatus() != MemberStatus.SUSPENDED;   // 정지면 로그인 거부
}
@Override public boolean isEnabled() {
    MemberStatus s = member.getMemberStatus();
    return s == MemberStatus.ACTIVE || s == MemberStatus.PENDING; // 탈퇴/휴면은 거부
}
@Override public Collection<? extends GrantedAuthority> getAuthorities() {
    return List.of(new SimpleGrantedAuthority("ROLE_" + member.getMemberType().name()));
}
```
→ 권한 문자열은 `ROLE_NORMAL` / `ROLE_SELLER` / `ROLE_ADMIN`. SecurityConfig의 `hasRole("ADMIN")`이 이 값과 매칭된다(`hasRole`은 자동으로 `ROLE_` 접두사를 붙여 비교).

## 3. Access 토큰 vs Refresh 토큰 — 왜 둘로 나누나

| | Access Token | Refresh Token |
|---|---|---|
| 수명 | **30분** (`1800000ms`) | **14일** (`1209600000ms`) |
| 담는 것 | `memberId` + `role` | `memberId`만 |
| 전달 | 응답 바디 → 프론트가 메모리/저장소 보관 후 `Authorization` 헤더로 | **HttpOnly 쿠키** |
| 저장 | 서버 보관 안 함 (Stateless) | **Redis에 저장**(`refresh:{memberId}`) |
| 용도 | 매 API 호출 인증 | Access 만료 시 새 Access 재발급 |

**왜 이렇게?**
- Access는 짧게 → 탈취돼도 30분이면 무력화. 매번 DB 안 보고 토큰만으로 통과.
- Refresh는 길게, 단 **HttpOnly 쿠키**로 → JS가 못 읽어 XSS에 안전. `secure`+`sameSite=Strict`+`path=/auth`로 범위 최소화.
- Refresh를 **Redis에도 저장**하는 이유: 로그아웃·정지 시 서버가 **강제 무효화**할 수 있어야 하기 때문(아래 §5).

[AuthController.java](../src/main/java/com/ticketing/auth/controller/AuthController.java) — Refresh 쿠키 설정:
```java
ResponseCookie.from("refreshToken", value)
    .httpOnly(true).secure(true).sameSite("Strict")
    .path("/auth")                       // /auth/refresh, /auth/logout 에만 전송
    .maxAge(Duration.ofDays(14)).build();
```

## 4. 토큰 발급/검증 — JwtTokenProvider

[JwtTokenProvider.java](../src/main/java/com/ticketing/auth/jwt/JwtTokenProvider.java)
```java
public String createAccessToken(Long memberId, String role) {
    return Jwts.builder()
        .subject(String.valueOf(memberId))   // sub = memberId
        .claim("role", role)                  // 커스텀 클레임
        .issuedAt(now).expiration(exp)
        .signWith(key)                        // HMAC-SHA 서명
        .compact();
}
public boolean validate(String token) {
    try { Jwts.parser().verifyWith(key).build().parseSignedClaims(token); return true; }
    catch (Exception e) { return false; }     // 만료/위조/형식오류 전부 false
}
```
- 비밀키는 `jwt.secret` (환경변수 `JWT_SECRET`, 32바이트 이상). `@PostConstruct`에서 `SecretKey`로 1회 변환.
- 서명 검증이 통과하면 위조되지 않은 토큰. 만료도 `parseSignedClaims`가 잡아 예외 → `false`.

## 5. 토큰 재발급(reissue)과 로그아웃 — Redis가 핵심

### 재발급 [AuthService.reissue()](../src/main/java/com/ticketing/auth/service/AuthService.java)
```java
public String reissue(String refreshToken) {
    if (refreshToken == null || !jwtTokenProvider.validate(refreshToken))   // 1) 서명·만료 검사
        throw new BaseException(UNAUTHORIZED_ACCESS);

    Long memberId = jwtTokenProvider.getMemberId(refreshToken);

    if (!refreshTokenStore.isValid(memberId, refreshToken))                 // 2) Redis와 일치?
        throw new BaseException(UNAUTHORIZED_ACCESS);

    Member member = memberRepository.findById(memberId).orElseThrow(...);
    if (status != ACTIVE && status != PENDING) {                           // 3) 그새 정지/탈퇴됐나
        refreshTokenStore.delete(memberId);
        throw new BaseException(UNAUTHORIZED_ACCESS);
    }
    return jwtTokenProvider.createAccessToken(memberId, role);             // 새 Access만 재발급
}
```
2번이 중요하다. 토큰 자체는 유효해도 **Redis에 저장된 것과 다르면 거부**한다. → 로그아웃하면 Redis에서 지우므로, 남아 있는 옛 Refresh 토큰으로는 재발급이 안 된다.

### 로그아웃 [AuthService.logout()](../src/main/java/com/ticketing/auth/service/AuthService.java)
```java
refreshTokenStore.delete(memberId);   // Redis 키 삭제 → 그 토큰은 즉시 무력화
```
+ 컨트롤러에서 `maxAge=0` 쿠키를 내려 브라우저 쿠키도 만료시킨다.

[RefreshTokenStore.java](../src/main/java/com/ticketing/auth/jwt/RefreshTokenStore.java) — `refresh:{memberId}` 키에 TTL 14일로 저장. Stateless의 단점(서버가 토큰을 못 끊음)을 Refresh만 Redis에 두어 보완한 절충안이다.

## 6. 다음 요청은 어떻게 "누구"를 아나 (인증 필터)

[02 요청의 생애 §2-②](02_요청_한번의_생애.md)에서 봤듯, `JwtAuthenticationFilter`가 매 요청 `Authorization: Bearer ...`를 까서 `SecurityContext`에 심는다. 그 덕분에 컨트롤러는:
```java
public ... create(..., @AuthenticationPrincipal CustomUserDetails user) {
    Long memberId = user.getMemberId();   // 토큰에서 추출된 그 사람
}
```
로 현재 사용자를 바로 꺼낸다. **컨트롤러는 토큰을 직접 파싱하지 않는다** — 필터가 이미 다 해뒀다.

> 참고: 필터는 `loadById(memberId)`로 **매 요청 DB를 한 번 조회**한다. 토큰의 role 클레임을 믿고 DB 조회를 생략하는 최적화도 가능하지만, 실시간 정지 반영을 위해 DB 조회를 택했다. (면접 포인트: 보안 최신성 vs 성능 트레이드오프)

## 7. 인가 — URL별 권한 매트릭스

[SecurityConfig.java](../src/main/java/com/ticketing/config/SecurityConfig.java) 발췌:

| 경로 | 메서드 | 권한 |
|---|---|---|
| `/auth/**` | * | 공개 |
| `/events`, `/events/**`, `/venues/**`, `/schedules/**` | GET | 공개(조회) |
| `/members/signup`, `/sellers/signup` | POST | 공개 |
| `/admin/**`, `POST /coupons`, `/venues`(쓰기) | * | `ADMIN` |
| `POST/PATCH/DELETE /events`, `POST /events/*/schedules`, `/sellers/me/**` | * | `SELLER` |
| 그 외 전부 (예매·결제·대기열·마이페이지·쿠폰발급·리뷰작성) | * | 로그인 필요 |

- 권한 미달 시: 미로그인 → 401(`UNAUTHORIZED_ACCESS`), 권한부족 → 403(`FORBIDDEN_ACCESS`). 둘 다 `BaseResponse` 포맷.
- **2차 방어선**: URL 레벨 인가를 통과해도, 서비스에서 "본인 것인가"를 한 번 더 검사한다. 예: `event.isOwnedBy(sellerId)`, `reservation.isOwnedBy(memberId)`. 셀러 A가 셀러 B의 공연을 수정하려 하면 `EVENT_NOT_OWNED`(403).

## 9. 자주 헷갈리는 개념 정리 (세션 · 쿠키 · 서명 · 확장 · CORS)

토큰/인증을 처음 보면 반드시 헷갈리는 것들을 모았다. 전부 면접 단골이다.

### ① 쿠키 vs 세션 vs JWT — "다른 축"이다
- **쿠키** = 그냥 **그릇 / 전송 수단** (브라우저가 값을 저장하고 요청마다 자동으로 보내는 통로).
- **세션** = 정보를 **서버**(맵/Redis)에 두고, 쿠키엔 **세션ID(열쇠)만** 담는다. 서버가 그 ID로 정보를 찾음 → **Stateful**.
- **JWT** = 정보를 **토큰 자체**에 담아 클라이언트가 들고 다닌다. 서버는 저장 안 하고 매 요청 토큰을 **까서(서명 검증)** 판단 → **Stateless**.

→ **"쿠키를 쓰냐"와 "세션이냐 토큰이냐"는 별개 축이다.** 쿠키는 그릇일 뿐, 정보를 서버에 두냐(세션) 토큰에 두냐(JWT)가 진짜 차이.

| 저장 위치 ↓ \ 전송 → | 쿠키 | 헤더 |
|---|---|---|
| 서버(세션) | 전통적 세션 | (드묾) |
| 토큰(JWT) | 우리 **Refresh** | 우리 **Access** |

→ 우리는 토큰을 쓰면서도 **Access는 `Authorization` 헤더, Refresh는 HttpOnly 쿠키**로 나눠 쓴다.

### ② JWT는 "암호화"가 아니라 "서명"이다
- 페이로드는 **Base64 인코딩**이라 **누구나 디코딩해 읽을 수 있다**(jwt.io에 붙이면 내용이 다 보임). "해독 가능" 맞다.
- JWT의 보안은 **내용 숨김(기밀성)이 아니라 위조 방지(무결성)**다. 서명은 **secret key**로 만들어, 페이로드를 바꾸면 **서명이 안 맞아 거부**된다. (변조 불가, 열람 가능)
- **그래서 민감정보(비밀번호 등)는 안 넣는다.** 우리 토큰엔 `memberId`·`role`만 — 노출돼도 무방.
- 탈취 대응은 별개 문제다: **전송 중 탈취 → HTTPS**, **저장된 토큰 탈취(XSS) → Refresh를 HttpOnly 쿠키로 + Access 수명 짧게(30분)**.
- (보너스) 진짜 내용을 숨기려면 JWE(암호화 JWT)도 있지만, 우리는 **JWS(서명만)** — 민감정보를 안 넣으면 이걸로 충분하다.

### ③ secret key는 "상태"가 아니라 "설정" — 그래서 확장에 유리
- 세션은 **매 로그인마다 생기고 사라지는 상태** → 서버 여러 대면 **실시간 동기화**(sticky session / Redis 중앙 세션)가 필요하다.
- secret key는 **안 변하는 설정** → 배포 때 모든 인스턴스에 **같은 값(환경변수 / AWS Parameter Store)** 을 한 번 주면 끝. **런타임 동기화가 필요 없다.**
- 이게 JWT가 수평 확장에 유리한 **진짜 이유**다. 서버는 토큰 서명만 검증하면 되고, 인스턴스끼리 공유해 맞춰야 할 "변하는 상태"가 없다. (secret 교체(rotation)는 가끔 있는 이벤트지, 세션처럼 매 요청 실시간이 아니다.)

### ④ CORS는 "서버 보안"이 아니라 "브라우저 정책"이다
- CORS(Cross-Origin Resource Sharing)는 **브라우저에서 실행되는 JS에만** 적용된다.
- **Postman · curl · 서버간 호출은 CORS를 무시하고 통과한다 → CORS는 이들을 못 막는다.**
- 실제 접근 통제는 **인증(JWT) · 인가 · RateLimit**이 한다. CORS는 **악성 사이트가 사용자의 인증정보(쿠키)로 우리 API를 호출해 응답을 빼가는 것**을 막는 용도다(서버 보호가 아니라 사용자 보호).
- `setAllowedOrigins`는 배포 시 실제 프론트 도메인으로 바꾼다(= 그 출처 웹사이트의 JS만 브라우저에서 응답을 읽게 허용). 단 이게 "모든 잘못된 요청을 막는 방패"는 아니다 — 그건 인증의 몫.

### ⑤ 왜 Access는 헤더, Refresh는 HttpOnly 쿠키인가 (XSS vs CSRF)

핵심: **헤더로 보내려면 JS가 토큰을 손에 쥐고 있어야 하는데, 그게 XSS에 취약하다.**

- **헤더(`Authorization: Bearer`)** 로 보내려면 → 프론트 JS가 토큰을 `localStorage`/메모리에 들고 있어야 함 → **JS 접근 가능 = XSS로 탈취 가능.**
- **HttpOnly 쿠키**는 → **JS가 못 읽는다**(`document.cookie`로도 안 보임) → **XSS로 못 훔침.** 그런데도 브라우저가 요청에 **자동으로** 실어 보낸다(JS가 토큰을 만질 필요 없음). ← **이게 쿠키에 담는 이득.**

**그래서 토큰 특성에 맞춰 저장/전송을 다르게 한다:**

| | Access | Refresh |
|---|---|---|
| 수명 | 30분(단명) | 14일(장수명) |
| 탈취 시 | 곧 만료, 피해 작음 | 오래 악용 → **치명적** |
| 저장/전송 | JS 메모리 + **헤더** | **HttpOnly 쿠키** |

→ 짧고 자주 쓰는 Access는 편하게(헤더), 길고 치명적인 Refresh는 **JS가 못 건드리게 격리**(HttpOnly 쿠키).

**근본은 XSS ↔ CSRF 트레이드오프다:**

| 방식 | XSS(스크립트 탈취) | CSRF(쿠키 자동전송 악용) |
|---|---|---|
| 헤더(Authorization) | ❌ 취약 (JS가 들고 있음) | ✅ 안전 (JS가 명시적으로 붙임) |
| 쿠키(HttpOnly) | ✅ 안전 (JS 접근 불가) | ❌ 취약 → `sameSite=Strict`로 막음 |

→ **Access=헤더**(CSRF 안전, XSS는 단명으로 감수) / **Refresh=HttpOnly 쿠키**(XSS 안전, CSRF는 `sameSite=Strict`+`path=/auth`로 보완). 쿠키 속성이 각각 한 가지씩 막는다 — `httpOnly`(XSS) · `secure`(전송 중 탈취) · `sameSite`(CSRF) · `path=/auth`(노출 범위 최소화).

---

## 10. 면접 한 줄 정리

> Stateless JWT로 세션 동기화 부담을 없애되, **Refresh 토큰만 Redis에 저장**해 로그아웃·정지 시 강제 무효화가 가능하게 했습니다. Access는 30분으로 짧게, Refresh는 HttpOnly 쿠키로 XSS에 안전하게 분리했습니다.
