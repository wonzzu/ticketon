# 06. 예매와 결제

> 좌석을 골라 예매하고 결제까지 가는 **전체 트랜잭션 흐름**과, 그 과정에서 정합성을 지키는 세 가지 장치
> (멱등성 키 / 대기열 통과 검사 / 좌석 선점 검증)를 설명한다.

---

## 1. 예매 → 결제, 두 단계로 나뉜다

```
좌석 선택
  │  POST /reservations  { scheduleId, eventSeatIds[], idempotencyKey }
  ▼
예매 생성 (Reservation: PENDING)        ← 좌석을 "내가 잡았다"고 선언 + 가격 확정
  │  POST /payments  { reservationId }
  ▼
결제 (Payment: PAID, Reservation: CONFIRMED, EventSeat: RESERVED)
```

왜 두 단계? 예매(좌석 점유)와 결제(돈)는 책임이 다르다. 예매로 잠깐 잡아두고(Redis HELD, 7분), 그 안에 결제하면 확정. 못 하면 점유가 풀린다.

## 2. 예매 생성 — 4개의 관문

[ReservationService.create()](../src/main/java/com/ticketing/reservation/service/ReservationService.java)
```java
@Transactional
public ReservationResponseDto create(Long memberId, ReservationCreateDto dto) {

    // ① 멱등성: 같은 키로 이미 예매했으면 새로 만들지 않고 그대로 반환
    Optional<Reservation> exist = reservationRepository.findByIdempotencyKey(dto.getIdempotencyKey());
    if (exist.isPresent()) return ReservationResponseDto.from(exist.get());

    // ② 대기열 통과자인가
    if (!queueService.isAdmitted(dto.getScheduleId(), memberId))
        throw new BaseException(QUEUE_NOT_ADMITTED);

    // ③ 좌석 개수/상태 검증
    List<Long> seatIds = dto.getEventSeatIds();
    if (seatIds.isEmpty())            throw new BaseException(EMPTY_SEAT_SELECTION);
    if (seatIds.size() > MAX_SEATS)   throw new BaseException(EXCEED_SEAT_LIMIT);   // 최대 3개
    List<EventSeat> seats = eventSeatRepository.findAllById(seatIds);
    if (seats.size() != seatIds.size()) throw new BaseException(SEAT_NOT_AVAILABLE);
    if (seats.stream().anyMatch(s -> s.getStatus() == RESERVED))
        throw new BaseException(SEAT_NOT_AVAILABLE);                                // 이미 팔린 좌석

    // ④ Redis 선점: 원자적으로 좌석 점유 (하나라도 실패하면 전부 롤백 후 실패)
    if (!seatHoldService.holdAll(dto.getScheduleId(), seatIds, memberId))
        throw new BaseException(SEAT_NOT_AVAILABLE);

    // 통과 → 예매 저장 (PENDING) + 이력
    int totalPrice = seats.stream().mapToInt(EventSeat::getPrice).sum();
    Reservation reservation = Reservation.create(member, schedule, dto.getIdempotencyKey(), totalPrice);
    for (EventSeat seat : seats) reservation.addReservationSeat(ReservationSeat.create(seat, seat.getPrice()));
    reservationRepository.save(reservation);
    reservationHistoryRepository.save(ReservationHistory.of(reservation));
    return ReservationResponseDto.from(reservation);
}
```

### 관문 ① 멱등성 — 왜 필요한가
네트워크가 끊겨 사용자가 "예매" 버튼을 두 번 누르거나, 응답을 못 받아 프론트가 재요청하면 **예매가 2건** 생길 수 있다. 클라이언트가 만든 `idempotencyKey`(주문 ID)를 UNIQUE 컬럼으로 두고, 같은 키면 **기존 예매를 그대로 반환**한다. → "같은 요청을 여러 번 해도 결과가 한 번 한 것과 같다."
```java
@Column(unique = true, nullable = false) private String idempotencyKey;  // Reservation
```

### 관문 ② 대기열 통과 검사
예매 진입은 대기열을 통과(`ADMITTED`)한 사람만. 통과 안 했으면 `QUEUE_NOT_ADMITTED`. → [08 대기열](08_대기열.md).

### 관문 ③ 좌석 상태 — DB 1차 방어
이미 `RESERVED`(결제 확정)된 좌석은 여기서 막는다. 단, 이건 **느슨한 1차 검사**다. 동시에 두 명이 같은 좌석을 고르면 둘 다 이 검사를 통과할 수 있다. 진짜 단 한 명만 잡게 하는 건 ④.

### 관문 ④ Redis 원자적 선점 — 진짜 동시성 방어
[SeatHoldService.holdAll()](../src/main/java/com/ticketing/event/service/SeatHoldService.java)
```java
public boolean holdAll(Long scheduleId, List<Long> eventSeatIds, Long memberId) {
    List<Long> heldByMe = new ArrayList<>();
    for (Long seatId : eventSeatIds) {
        Boolean ok = redisTemplate.opsForValue()
            .setIfAbsent(key(scheduleId, seatId), memberId.toString(), HOLD_TTL);  // SET NX, 원자적
        if (Boolean.TRUE.equals(ok)) heldByMe.add(seatId);
        else { releaseAll(scheduleId, heldByMe); return false; }   // 하나라도 실패 → 내가 잡은 것 전부 반납
    }
    return true;
}
```
`setIfAbsent`(Redis `SET NX`)는 원자적이라 동시에 와도 **단 한 명만** 성공한다. 여러 좌석을 잡다 중간에 실패하면 이미 잡은 걸 되돌려(부분 점유 방지) `false`. 동작 원리는 [07 좌석선점](07_좌석선점_Redis.md)에서 깊게.

> 트랜잭션 주의(면접 포인트): Redis 선점은 DB 트랜잭션 바깥의 부수효과다. ④ 이후 DB 저장이 실패하면 Redis 점유는 TTL(7분)로 자연 만료된다. 점유는 어차피 임시 데이터라 이 정도 보상이 적절하다고 봤다.

## 3. 결제 — 확정 짓기

[PaymentService.pay()](../src/main/java/com/ticketing/payment/service/PaymentService.java)
```java
@Transactional
public PaymentResponseDto pay(Long memberId, PaymentCreateDto dto) {
    Reservation reservation = ...;
    if (!reservation.isOwnedBy(memberId))                 throw new BaseException(RESERVATION_NOT_OWNED);
    if (paymentRepository.existsByReservationId(...))     throw new BaseException(PAYMENT_ALREADY_COMPLETED); // 중복 결제 차단

    // ① 아직 내가 선점 중인가 (7분 안에 결제하는가)
    if (!seatHoldService.isHeldByAll(scheduleId, seatIds, memberId))
        throw new BaseException(SEAT_HOLD_EXPIRED);

    // ② 좌석을 DB에서 확정 점유 (AVAILABLE → RESERVED, 불변식 검사 포함)
    reservation.getReservationSeats().forEach(rs -> rs.getEventSeat().reserve());

    // ③ 결제 생성 + 이력
    Payment payment = Payment.paid(reservation, reservation.getTotalPrice());
    paymentRepository.save(payment);
    paymentHistoryRepository.save(PaymentHistory.of(payment, null));

    // ④ 예매 확정 (PENDING → CONFIRMED) + 이력
    reservation.confirm();
    reservationHistoryRepository.save(ReservationHistory.of(reservation));

    // ⑤ Redis 임시 점유 해제 (이제 DB의 RESERVED가 진실)
    seatHoldService.releaseAll(scheduleId, seatIds);
    return PaymentResponseDto.from(payment);
}
```

핵심은 **점유의 주체가 바뀌는 순간**이다.
- 결제 전: 점유 = **Redis HELD**(임시, TTL 7분).
- 결제 후: 점유 = **DB의 `EventSeat.status = RESERVED`**(영구). Redis 점유는 더 이상 필요 없어 해제.

`isHeldByAll`로 "내 점유가 아직 살아있나"를 먼저 확인한다. 7분이 지나 TTL 만료됐으면 `SEAT_HOLD_EXPIRED` → 다른 사람이 그새 잡았을 수 있으니 결제 거부.

> 실제 PG는 후순위라 `Payment.paid()`는 `method="MOCK"`으로 모의 결제다. 멱등성 키 흐름은 PG 콜백을 붙일 때도 그대로 쓸 수 있게 설계했다.

## 4. 예매 취소 — 점유와 결제를 함께 되돌린다

[ReservationService.cancel()](../src/main/java/com/ticketing/reservation/service/ReservationService.java)
```java
@Transactional
public void cancel(Long reservationId, Long memberId, CancelReason cancelReason, String detail) {
    if (cancelReason == CancelReason.OTHER && (detail == null || detail.isBlank()))
        throw new BaseException(CANCEL_DETAIL_REQUIRED);     // '기타' 사유는 상세 필수

    Reservation reservation = ...;
    if (!reservation.isOwnedBy(memberId)) throw new BaseException(RESERVATION_NOT_OWNED);

    reservation.cancel();                                                    // CONFIRMED → CANCEL
    reservation.getReservationSeats().forEach(rs -> rs.getEventSeat().cancel()); // RESERVED → AVAILABLE
    seatHoldService.releaseAll(scheduleId, seatIds);                         // 혹시 남은 Redis 점유도 정리

    paymentRepository.findByReservationId(reservationId).ifPresent(payment -> {
        payment.cancel();                                                    // PAID → CANCELED
        paymentHistoryRepository.save(PaymentHistory.of(payment, cancelReason.getDescription()));
    });
    reservationHistoryRepository.save(ReservationHistory.ofCancel(reservation, cancelReason, detail));
}
```
좌석을 다시 `AVAILABLE`로 풀어 재판매되게 하고, 결제·예매 모두 상태 전이 + 이력을 남긴다. 취소 사유(`CancelReason` ENUM)와 상세를 이력에 기록한다.

## 5. 상태로 관리하는 생명주기 (SOFT DELETE 아님)

CLAUDE.md §6.2대로, 예매·결제는 행을 지우지 않고 **상태**로 관리한다.

| 엔티티 | 상태 | 의미 |
|---|---|---|
| `Reservation` | `PENDING → CONFIRMED → CANCEL` | 결제 대기 → 완료 → 취소 |
| `Payment` | `PAID / FAILED / CANCELED` | 단순 삭제가 아니라 생명주기 |
| `EventSeat` | `AVAILABLE / HELD / RESERVED` | 재판매 가능 / 임시점유(Redis) / 확정점유(DB) |

상태 전이는 전부 엔티티 메서드 + 불변식: `reservation.confirm()`은 `PENDING`일 때만, `payment.cancel()`은 `PAID`일 때만 등.

## 7. 정합성 장치 한눈에 (면접 정리)

| 위협 | 장치 | 어디 |
|---|---|---|
| 중복 예매(더블클릭/재요청) | **멱등성 키**(UNIQUE) | `findByIdempotencyKey` |
| 같은 좌석 동시 클릭 | **Redis `SET NX` 원자 선점** | `holdAll` |
| 정원 초과 진입 | **대기열 통과 검사** | `isAdmitted` |
| 선점 만료 후 뒷북 결제 | **`isHeldByAll` 검사** | `pay` |
| 중복 결제 | **`existsByReservationId`** | `pay` |
| 분쟁(가격·상태) 추적 | **이력 테이블 스냅샷** | `ReservationHistory`/`PaymentHistory` |

> 면접 한 줄: 예매는 멱등성 키로 중복을, Redis `SET NX`로 좌석 동시성을 막고, 점유 주체를 결제 전 Redis(TTL) → 결제 후 DB(RESERVED)로 넘기는 2단계로 설계했습니다. 모든 상태 변화는 이력 테이블에 스냅샷으로 남깁니다.
