# 02. 요청 한 번의 생애

> HTTP 요청 하나가 들어와서 응답이 나가기까지 **거쳐 가는 모든 관문**을 순서대로 따라간다.
> 이걸 알면 나머지 챕터의 코드가 "전체 흐름 중 어느 단계 얘기인지" 감이 잡힌다.

---

## 1. 큰 그림

```
[브라우저]
   │  POST /reservations  { ... }   Authorization: Bearer xxx
   ▼
①  CORS 필터            ── 허용된 출처(localhost:5173)인가
   ▼
②  JwtAuthenticationFilter ── 토큰 까서 "이 사람 누구"를 SecurityContext에 심음
   ▼
③  Security 인가 검사    ── 이 URL은 로그인/권한이 필요한가
   ▼
④  Controller           ── @Validated로 형식 검증, DTO로 받음
   ▼
⑤  Service (@Transactional) ── 비즈니스 로직, 트랜잭션 경계
   ▼
⑥  Domain + Repository  ── 도메인 규칙 실행, DB 반영
   ▼
⑦  Response DTO         ── 엔티티 → 응답 변환
   ▼
⑧  BaseResponse로 감쌈   ── { success, code, message, data }
   ▼
(예외 발생 시) GlobalExceptionHandler가 가로채서 동일 포맷으로 변환
   ▼
[브라우저]  응답 JSON
```

---

## 2. 단계별 상세

### ① CORS — 누가 부르는가
[SecurityConfig.java](../src/main/java/com/ticketing/config/SecurityConfig.java)
```java
config.setAllowedOrigins(List.of("http://localhost:5173"));   // Vue dev 서버만 허용
config.setAllowCredentials(true);                              // 쿠키(refreshToken) 주고받기 허용
config.setExposedHeaders(List.of("Authorization", "Set-Cookie"));
```
프론트(5173)와 백엔드(8080)가 포트가 달라 브라우저가 막는 걸 풀어준다. `allowCredentials=true`라서 리프레시 토큰 쿠키가 오갈 수 있다.

### ② JwtAuthenticationFilter — "이 사람 누구"
[JwtAuthenticationFilter.java](../src/main/java/com/ticketing/auth/jwt/JwtAuthenticationFilter.java)

`OncePerRequestFilter`라서 요청당 딱 한 번 돈다. 흐름:
```java
String token = resolveToken(request);                 // "Bearer " 떼고 토큰만
if (hasText(token) && jwtTokenProvider.validate(token)) {
    Long memberId = jwtTokenProvider.getMemberId(token);
    UserDetails userDetails = customUserDetailsService.loadById(memberId);  // DB에서 회원 조회
    UsernamePasswordAuthenticationToken auth = new UsernamePasswordAuthenticationToken(
        userDetails, null, userDetails.getAuthorities());
    SecurityContextHolder.getContext().setAuthentication(auth);   // ★ 여기에 심어두면
}
filterChain.doFilter(request, response);
```
- 토큰이 없거나 틀려도 **여기서 막지 않는다.** 그냥 인증 정보를 안 심고 통과시킨다. 막는 건 다음 단계(③)의 책임.
- 한 번 심어두면 이후 Controller에서 `@AuthenticationPrincipal CustomUserDetails user`로 바로 꺼내 쓸 수 있다.
- 자세한 내부는 [03 인증/인가](03_인증인가.md).

### ③ Security 인가 — 들어갈 자격이 있나
[SecurityConfig.java](../src/main/java/com/ticketing/config/SecurityConfig.java)
```java
.requestMatchers("/auth/**").permitAll()                        // 로그인은 누구나
.requestMatchers(HttpMethod.GET, "/events", "/events/**").permitAll()  // 공연 조회는 공개
.requestMatchers("/admin/**").hasRole("ADMIN")                  // 어드민 전용
.requestMatchers(HttpMethod.POST, "/events").hasRole("SELLER")  // 공연 등록은 셀러
.anyRequest().authenticated()                                   // 그 외 전부 로그인 필요
```
- 자격 미달이면 여기서 끊긴다:
  - 로그인 안 함 → `JwtAuthenticationEntryPoint` → **401** + `BaseResponse(UNAUTHORIZED_ACCESS)`
  - 권한 부족 → `JwtAccessDeniedHandler` → **403** + `BaseResponse(FORBIDDEN_ACCESS)`
- 두 핸들러 모두 에러조차 `BaseResponse` 포맷으로 내려준다. 프론트는 성공/실패 응답을 **항상 같은 모양**으로 받는다.

### ④ Controller — 형식 검증 + DTO 수령
```java
@PostMapping
public ResponseEntity<BaseResponse<ReservationResponseDto>> create(
        @Validated @RequestBody ReservationCreateDto dto,
        @AuthenticationPrincipal CustomUserDetails user) {
    ReservationResponseDto data = reservationService.create(user.getMemberId(), dto);
    return ResponseEntity.status(HttpStatus.CREATED).body(BaseResponse.success(data));
}
```
- `@Validated` + DTO의 `@NotNull`·`@NotEmpty`·`@Email` 같은 어노테이션이 **형식 검증**을 한다.
  - 형식 위반 → `MethodArgumentNotValidException` → GlobalExceptionHandler → **400** `INVALID_INPUT`.
- 비즈니스 규칙 검증(좌석 3개 초과 등)은 여기가 아니라 Service/Domain에서 한다.

### ⑤⑥ Service + Domain — 진짜 일
[ReservationService.create()](../src/main/java/com/ticketing/reservation/service/ReservationService.java)
```java
@Transactional
public ReservationResponseDto create(Long memberId, ReservationCreateDto dto) {
    // 1) 멱등성: 같은 키면 기존 예매 그대로 반환 (중복 생성 방지)
    // 2) 대기열 통과자인지 검사
    // 3) 좌석 개수/상태 검증 → Redis 선점 → 예매 저장 → 이력 저장
}
```
- `@Transactional` 메서드 안에서 던진 `BaseException`은 자동 롤백된다(RuntimeException 계열).
- 도메인 규칙은 엔티티에 위임: `reservation.confirm()`, `seat.reserve()` 등.

### ⑦⑧ 응답 변환 + 래핑
[ReservationResponseDto.from()](../src/main/java/com/ticketing/reservation/dto/response/ReservationResponseDto.java) 가 엔티티를 응답용으로 바꾸고, Controller가 `BaseResponse.success(data)`로 감싼다.

## 3. 공통 응답 포맷 — BaseResponse

[BaseResponse.java](../src/main/java/com/ticketing/global/baseresponse/BaseResponse.java)
```java
public class BaseResponse<T> {
    private boolean success;
    private int code;        // 1000=성공, 2001=중복이메일 …
    private String message;
    private T data;
}
```
성공:
```json
{ "success": true, "code": 1000, "message": "성공", "data": { ... } }
```
실패:
```json
{ "success": false, "code": 4004, "message": "최대 3개 좌석까지 예매할 수 있습니다", "data": null }
```

> ⚠️ 프론트 CLAUDE.md의 가정(`code`가 문자열, `timestamp` 있음)과 **실제 구현이 다르다.** 실제는 `code`가 **정수**고 `timestamp` 필드는 없다. 프론트 인터셉터 매핑 시 이 점을 맞춰야 한다. (자세히는 §5)

### 에러 코드는 한 곳에 모음
[BaseResponseStatus.java](../src/main/java/com/ticketing/global/baseresponse/BaseResponseStatus.java) — 도메인별 번호 대역으로 관리:

| 대역 | 도메인 | 예시 |
|---|---|---|
| 1000 | 공통 | `SUCCESS` |
| 2000 | 회원 | `DUPLICATE_EMAIL`, `MEMBER_NOT_FOUND` |
| 3000 | 공연 | `PERFORMANCE_NOT_FOUND`, `EVENT_NOT_OWNED` |
| 4000 | 예매 | `SEAT_NOT_AVAILABLE`, `EXCEED_SEAT_LIMIT` |
| 5000 | 결제 | `PAYMENT_ALREADY_COMPLETED` |
| 6000 | 대기열 | `QUEUE_NOT_ADMITTED` |
| 7000 | 리뷰 | `DUPLICATE_REVIEW` |
| 8000 | 쿠폰 | `COUPON_SOLD_OUT` |
| 9000 | 서버 | `INTERNAL_SERVER_ERROR`, `TOO_MANY_REQUESTS` |

각 status는 `code`(앱 내부 코드) + `httpStatus`(HTTP 상태)를 **둘 다** 들고 있어, 핸들러가 HTTP 상태와 바디 코드를 일관되게 내려준다.

## 4. 예외는 어떻게 일관된 모양이 되나

[GlobalExceptionHandler.java](../src/main/java/com/ticketing/global/exception/GlobalExceptionHandler.java)
```java
@ExceptionHandler(BaseException.class)             // 우리가 의도한 비즈니스 예외
ResponseEntity<...> handleBaseException(BaseException e) {
    BaseResponseStatus status = e.getStatus();
    return ResponseEntity.status(status.getHttpStatus()).body(BaseResponse.error(status));
}

@ExceptionHandler(MethodArgumentNotValidException.class)  // @Validated 실패
// → 400 INVALID_INPUT

@ExceptionHandler(Exception.class)                 // 미처 못 잡은 모든 것
// → 500 INTERNAL_SERVER_ERROR (스택트레이스는 log.error로만, 사용자에겐 노출 X)
```
- 핵심: **어디서 터지든** 사용자는 항상 `BaseResponse` 모양으로 받는다.
- 비즈니스 예외(`BaseException`)는 `log.warn`, 예상 못 한 예외는 `log.error`로 구분해 남긴다.

## 5. 프론트가 알아야 할 것 (개발자 읽는 영역)

- **언래핑**: 인터셉터에서 `response.data.data`만 호출부로 반환 → 호출부는 래퍼를 의식 안 함.
- **에러 판별**: `success === false`로 분기, `code`(정수) + `message`로 토스트.
- **401**: 로그아웃 + 로그인 페이지. **403**: 권한 없음 안내. **429**(`TOO_MANY_REQUESTS`): 잠시 후 재시도 안내.
- **페이지네이션 응답**: `/reservations/me`, `/admin/members`는 `data`가 Spring `Page` 객체(`content`, `totalElements`, `number`, `size` …)다.
