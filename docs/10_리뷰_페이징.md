# 10. 리뷰와 페이징

> 리뷰 도메인을 통해 이 프로젝트의 **페이징·정렬·동적 쿼리(QueryDSL) 공통 패턴**을 정리한다.
> 리뷰 자체는 단순하지만, 여기 쓰인 조회 기법들이 예매·회원·랭킹 등 곳곳에서 반복되므로 한 번에 묶어 본다.

---

## 1. 리뷰 도메인 — 한 사람이 한 공연에 한 번

[Review.java](../src/main/java/com/ticketing/review/domain/Review.java)
```java
@Table(uniqueConstraints = @UniqueConstraint(
    name = "uk_review_member_event", columnNames = {"member_id", "event_id"}))  // ★ 1인 1리뷰
@SQLRestriction("deleted_at IS NULL")                                           // SOFT DELETE
public class Review extends BaseEntity {
    @ManyToOne(fetch = LAZY) private Event event;
    @ManyToOne(fetch = LAZY) private Member member;
    private Integer rating;     // 1~5
    private String content;
    private LocalDateTime deletedAt;

    public static Review create(Event event, Member member, int rating, String content) {
        validateRating(rating);                          // 불변식: 1~5 벗어나면 INVALID_REVIEW_RATING
        return Review.builder()...build();
    }
    public void delete() { this.deletedAt = LocalDateTime.now(); }   // SOFT
}
```
- **UNIQUE(member_id, event_id)**로 한 사람이 같은 공연에 두 번 못 쓰게 DB가 막는다. 서비스에서도 `existsByEventIdAndMemberId`로 선검사(`DUPLICATE_REVIEW`) — 앱 + DB 이중 방어.
- 별점 범위(1~5)는 엔티티 불변식. 신고·복구 대비 SOFT DELETE([05 §2](05_공연_좌석.md)와 동일 패턴).

[ReviewService](../src/main/java/com/ticketing/review/service/ReviewService.java) · [ReviewController](../src/main/java/com/ticketing/review/controller/ReviewController.java):
`GET/POST /events/{id}/reviews`, `DELETE /reviews/{id}`(본인만 — `REVIEW_NOT_OWNED`), `GET /me/reviews`.

## 2. 페이징 — Spring Data `Pageable`

리뷰 목록은 페이지로 끊어 준다.
[ReviewController.findAll()](../src/main/java/com/ticketing/review/controller/ReviewController.java)
```java
@GetMapping("/events/{eventId}/reviews")
public ... findAll(@PathVariable Long eventId,
                   @RequestParam(defaultValue = "latest") String sort,
                   @PageableDefault(size = 10) Pageable pageable) { ... }
```
- `@PageableDefault(size = 10)` → 기본 10개씩. 요청은 `?page=0&size=10&` 형태.
- 응답 `data`는 Spring `Page` 객체: `content`(목록) + `totalElements` + `totalPages` + `number`(현재 페이지) + `size`. 프론트는 이걸로 페이지네이터를 그린다.

> 이 `Page<...>`가 그대로 [02 §3 BaseResponse](02_요청_한번의_생애.md)의 `data`에 담긴다. 예매 목록(`/reservations/me`), 어드민 회원 검색(`/admin/members`)도 동일.

## 3. 정렬 — 메서드 분기 vs 동적 쿼리

리뷰 정렬은 "최신순 / 평점순" 두 가지. 단순해서 **Spring Data 메서드 이름**으로 처리한다.
[ReviewService.findByEvent()](../src/main/java/com/ticketing/review/service/ReviewService.java)
```java
Page<Review> reviews = "rating".equals(sort)
    ? reviewRepository.findByEventIdOrderByRatingDesc(eventId, pageable)      // 평점순
    : reviewRepository.findByEventIdOrderByCreatedAtDesc(eventId, pageable);  // 최신순(기본)

long count = reviewRepository.countByEventId(eventId);
Double averageRating = reviewRepository.findAverageRating(eventId);          // @Query AVG
return ReviewListResponseDto.of(count, averageRating, reviews);              // 목록+총개수+평균별점
```
[ReviewRepository](../src/main/java/com/ticketing/review/repository/ReviewRepository.java)는 메서드 이름 규칙(`findBy...OrderBy...Desc`)으로 쿼리를 자동 생성하고, 평균은 `@Query("select avg(r.rating) ...")`로 뽑는다.

> 정렬 후보가 2개라 메서드 분기로 충분. 조건이 늘면 다음 절의 QueryDSL로 간다.

## 4. 동적 쿼리 — QueryDSL 공통 패턴

검색 조건이 **있을 수도, 없을 수도** 있을 때(이메일·기간·상태 필터 등)는 QueryDSL을 쓴다. 이 프로젝트의 표준 패턴:

```
XxxRepository  (JpaRepository + XxxRepositoryCustom)   ← 진입점
XxxRepositoryCustom  (인터페이스)                       ← 커스텀 메서드 선언
XxxRepositoryImpl  (JPAQueryFactory 구현)               ← 실제 동적 쿼리
```

대표 예 — 회원 검색 [MemberRepositoryImpl](../src/main/java/com/ticketing/member/repository/MemberRepositoryImpl.java)
```java
queryFactory.selectFrom(member)
    .where(emailContains(cond.email()),     // 값 없으면 null 반환
           nameContains(cond.name()),
           statusEq(cond.memberStatus()),
           typeEq(cond.memberType()))
    .orderBy(member.createdAt.desc())
    .offset(pageable.getOffset()).limit(pageable.getPageSize())
    .fetch();

private BooleanExpression emailContains(String email) {
    return StringUtils.hasText(email) ? member.email.contains(email) : null;   // ★ null이면 조건 무시
}
```
**핵심 트릭**: 조건 메서드가 값 없을 때 `null`을 반환하면, QueryDSL `where(null)`은 그 조건을 **그냥 빼버린다**. 그래서 `if`문 떡칠 없이 "입력된 필터만 AND로" 붙는 동적 검색이 깔끔하게 된다.

### 페이징 count 최적화
```java
JPAQuery<Long> countQuery = queryFactory.select(member.count()).from(member).where(같은 조건);
return PageableExecutionUtils.getPage(result, pageable, countQuery::fetchOne);
```
`PageableExecutionUtils`는 **마지막 페이지거나 결과가 한 페이지 안에 들어오면 count 쿼리를 생략**한다. 불필요한 `COUNT(*)`를 안 날려 페이징 비용을 줄인다. → 예매 검색 [ReservationRepositoryImpl](../src/main/java/com/ticketing/reservation/repository/ReservationRepositoryImpl.java)도 동일.

같은 동적 쿼리 패턴이 쓰인 곳: 회원 검색, 예매 목록, 공연 검색([05 §6](05_공연_좌석.md)), 결제 매출 집계([12](12_이력_통계_배치.md)).

## 5. 평점순 랭킹 — GROUP BY + HAVING

"리뷰 평점 높은 공연 TOP N"은 QueryDSL 집계로 뽑는다.
[ReviewRepositoryImpl.findTopRatedEventIds()](../src/main/java/com/ticketing/review/repository/ReviewRepositoryImpl.java)
```java
queryFactory.select(review.event.id)
    .from(review)
    .where(review.event.status.eq(APPROVED))
    .groupBy(review.event.id)
    .having(review.count().goe(minReviews))                      // 리뷰 10개 이상인 공연만 (신뢰성)
    .orderBy(review.rating.avg().desc(), review.count().desc())  // 평균 평점 ↓, 동점이면 리뷰 수 ↓
    .limit(limit)
    .fetch();
```
- **`HAVING count >= 10`**: 리뷰 1개에 별 5점인 공연이 1등 하는 걸 막는다. 최소 표본을 강제해 랭킹 신뢰도를 높임.
- 정렬 2단(평균 → 동점 시 개수)로 합리적 순위.
- 이건 [12 통계·랭킹](12_이력_통계_배치.md)의 `getRanking(sort="rating")` 경로다. "인기순"(판매량)은 통계 테이블에서, "평점순"은 이 리뷰 집계에서 온다.

## 6. 면접 한 줄 정리

> 조회는 단순 정렬이면 Spring Data 메서드, 동적 조건이면 QueryDSL `BooleanExpression`이 null이면 조건을 빼는 패턴으로 통일했습니다. 페이징은 `PageableExecutionUtils`로 불필요한 count를 생략하고, 평점 랭킹은 `HAVING count >= 10`으로 최소 표본을 강제해 신뢰도를 확보했습니다.
