# 00. 프로젝트 개요

> 이 문서는 이 프로젝트를 **처음 받은 사람**이 0번부터 순서대로 읽으면 전체가 이해되도록 쓴 해설서다.
> 코드를 짠 본인의 복습용이자, 면접관·협업자에게 "왜 이렇게 짰는지"를 보여주는 지도다.

---

## 1. 이게 뭐 하는 프로젝트인가

콘서트·뮤지컬·전시·스포츠 공연을 **예매하는 티켓팅 사이트**다.

겉모습은 평범한 예매 사이트지만, 만든 목적은 화면이 아니라 **백엔드에서 터지는 어려운 문제들**을 직접 풀어보는 데 있다:

- **한 좌석에 동시에 여러 명이 몰릴 때** 어떻게 단 한 명만 잡게 할 것인가 (좌석 선점 정합성)
- **수만 명이 동시에 예매 버튼을 누를 때** 서버가 안 죽게 어떻게 줄을 세울 것인가 (대기열, 트래픽 평탄화)
- **선착순 쿠폰 100장**을 어떻게 101장 발급 안 되게 막을 것인가 (재고 동시성)

즉 **"많은 사람이 동시에 같은 자원을 노릴 때 생기는 충돌"** 을 다루는 게 이 프로젝트의 진짜 주제다. 이걸 주로 **Redis**로 푼다.

## 3. 기술 스택

**백엔드** (이 프로젝트의 본체)
- **Java 21 / Spring Boot 3.4.1**
- **Spring Data JPA + QueryDSL 5.1** — DB 접근. 정적 쿼리는 JPA, 동적 쿼리는 QueryDSL
- **MySQL** — 메인 DB (테스트는 H2 인메모리)
- **Redis + Redisson** — 선점·대기열·쿠폰·캐시·RateLimit·리프레시토큰. Redisson은 분산락용
- **Spring Security + JWT(jjwt)** — 인증/인가. 세션 안 쓰는 Stateless 방식
- **Micrometer + Prometheus + Grafana** — 모니터링. p6spy로 실행 SQL 추적

**프론트엔드** (화면)
- **Vue 3 (`<script setup>`) + Vite + Pinia + Vue Router + Axios + Bootstrap 5.3**

## 4. 패키지 구조 — 큰 지도

```
com.ticketing
├── auth         인증/인가      로그인, JWT 발급·검증, 리프레시 토큰
├── member       회원           일반회원 / 셀러 / 어드민 (상속 구조)
├── venue        공연장(물리)   Venue(공연장) + Seat(물리 좌석 배치)
├── event        공연(판매)     Event(공연) + EventSchedule(회차) + EventSeat(판매 좌석) + 좌석선점
├── reservation  예매           예매 생성, 멱등성, 좌석 연결
├── payment      결제           모의 결제, 예매와 1:1
├── coupon       쿠폰           선착순 발급
├── queue        대기열         줄 세우기 + 순번
├── review       리뷰           공연 후기, 평점
├── statistics   통계           일별 매출/공연 집계
├── admin        어드민         공연 검수, 회원 관리
├── global       공통           BaseResponse(응답 포맷), BaseEntity, 예외처리, RateLimit
└── config       설정           Security, Redisson, JPA Auditing
```

### 여기서 한 번 멈추고 알아둘 것 — `venue`와 `event`의 차이
처음 보면 헷갈리는 핵심 설계다.

- **`venue` = 물리적 실체**: "잠실 종합운동장에 좌석이 이렇게 배치돼 있다"(`Venue`, `Seat`). 공연과 무관하게 **건물처럼 고정**.
- **`event` = 판매 단위**: "그 공연장에서 7월 1일 19:30에 아이유 콘서트 1회차가 열리고, 그 회차의 A열 1번 좌석은 9.9만 원에 판다"(`Event`, `EventSchedule`, `EventSeat`).

즉 **물리 좌석(`Seat`) 하나가, 회차마다 판매용 좌석(`EventSeat`)으로 새로 찍힌다.** 같은 좌석이라도 회차가 다르면 다른 판매 좌석이다. 이 구분 덕분에 "공연장은 그대로 두고 공연만 갈아끼우기"가 된다. (자세히는 [05](05_공연_좌석.md))

### 도메인 내부는 항상 같은 계층 구조
```
<도메인>/
├── domain/        엔티티·ENUM (DB와 매핑되는 핵심 모델)
├── dto/
│   ├── request/   들어오는 데이터 (검증)
│   └── response/  나가는 데이터 (엔티티 → 응답 변환)
├── repository/    DB 접근
├── service/       비즈니스 로직 (트랜잭션 경계)
└── controller/    HTTP 진입점
```
**왜 `domain`과 `dto`를 폴더로 분리했나?** 엔티티가 DTO를 import하면 잘못된 의존(도메인이 바깥을 알게 됨)인데, 폴더가 갈려 있으면 **import 한 줄만 봐도 위반이 보인다.** (자세히는 [01](01_패키지구조_계층.md))

처음이라면 **번호 순서대로** 읽는 걸 권한다. 특히 앞의 세 개가 토대다:

1. **[02 요청 한 번의 생애](02_요청_한번의_생애.md)** — HTTP 요청 하나가 들어와서 응답이 나가기까지의 전체 흐름. 이걸 알면 나머지 챕터의 코드가 "어느 단계 얘기인지" 감이 잡힌다.
2. **[01 패키지 구조와 계층](01_패키지구조_계층.md)** — 왜 이렇게 폴더를 나눴고 의존이 어느 방향으로 흐르는지.
3. **[03 인증/인가](03_인증인가.md)** — 로그인하면 무슨 일이 벌어지고, 그 다음 요청은 어떻게 "이 사람 누구인지" 아는지.
